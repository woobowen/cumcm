# RC8 fresh C episode protocol — frozen before input

Registration inherits `initial_registration.json`: planned denominator **2**, serial 2016 C then
2015 C, 2014 C only for its three predeclared pre-result input/contamination reasons. No topic,
title, model recipe, data feature or answer is registered here. Difficulty is not a substitution
reason. Candidate acceptance and verified remote freeze precede all fresh input reading.

The same accepted implementation file mapping, Skill, shared rules/contracts/controller and
`environment.json` apply to both cases. The environment is an observed existing Linux/WSL Python
environment, not a portable lockfile. No package installation is planned during Validation.
The repository Python distribution remains 0.2.3; competition labels do not imply distribution
installation. Model-prior exposure is unverifiable. Filesystem isolation is by policy, and fresh
native worker context uses `fork_turns=none`; neither implies OS sandbox isolation.

Each case owns one complete 7,200-second window including input registration, reading, research,
pre-run freeze, execution, final evaluation, review and terminal freeze. Main records the actual
start/deadline, never resets it. Start case two only with at least 8,100 seconds before the global
2026-09-09T01:46:50Z deadline. Unused time from actual completion may be released. Otherwise retain
`NOT_RUN_BUDGET` against the original denominator. No waiting to inflate elapsed time.

The native worker receives only this generic protocol, frozen Skill and generic startup framework,
its own official raw input paths and its conflict-free case paths. It must not read Development
results, previous Validation reports, root developer task recipes, peer outputs, solutions, papers,
answers or benchmark vaults. It may read the frozen core/templates/controller to understand the
declared API. It may not alter shared files, global state, registry, formal decisions or Git.
The main agent handles source registration, commits, remote verification and formal acceptance.
The worker acts as the case modeling orchestrator and may update only its own case state.

Before main numerical results, the worker proposes a case-specific pre-run protocol: every main
question, actual evidence needs, audited data/provenance, model candidates and baseline rationale,
appropriate comparison and Final method, seeds, numeric tolerances, perturbations, actual execution
budget and a stop rule. The protocol and case code are committed by main; main confirms the
pre-run remote SHA before the worker starts model captures. Normal bounded case debugging and
comparison are allowed before Final, with every attempt, failure and revision preserved. At most
3 consecutive failed repairs of the same cause; unresolved shared-code gaps terminate or limit
the case, and cannot be fixed inside the frozen Validation episode.

Attempt all 14 Skill stages in order. A blocked prerequisite cannot be crossed to manufacture
later accepted artifacts; record later stages `NOT_REACHED` and an explicit terminal limitation.
Before Final, lock the actual selected Run/config/preprocessing and decision. No Final-driven
tuning, erased failure, repeat Final access or post-terminal Run. Final evaluation must match
the mathematical task: genuine prediction holdout or independent nonpredictive recomputation;
no fabricated labels/splits and no renaming prediction to descriptive to bypass validation.

After the worker fixes a terminal candidate package, it stops numerical work. A fresh native
read-only reviewer gets only this case's fixed input/code/output/Claim/handoff bundle and rubric,
checks mathematical adequacy, missing main questions, source sufficiency, constraints/objectives,
independence, leakage, and actual gate trace. It records actual reads and commands. Main then
freezes the terminal decision; a reviewer opinion cannot override an automated technical rejection.

The generic rubric has separate dimensions:

- **Started**: official inputs registered and the native worker begins its one-shot episode.
- **Actually executed**: at least one hash/Git-bound model capture, with all failures counted.
- **Episode completed**: a fixed reviewed terminal package and immutable decision, including
  failure or insufficient evidence. Completion alone is not a scientific PASS.
- **Technical gates**: actual CLI/controller evidence and artifact contracts; READY/JSON/CI alone
  never establishes mathematical or empirical correctness.
- **Scientific PASS**: every primary question answered at its actual requested strength, necessary
  data and model assumptions supported, appropriate final numerical/empirical checks passed,
  no material unresolved scientific objection, and passing machine gates. Missing main-question
  evidence yields INSUFFICIENT/PARTIAL/FAIL even when limited local Claims are supported.
- **Generalization**: report 2016 and 2015 separately and use the fixed denominator 2. Any observed
  success is limited evidence on these cases, not broad generalization or contest qualification.

All official raw content stays immutable and ignored. Publish derived first-party code, hash
manifests, counts, results, limitations, search/use ledgers and native review evidence. Answers
remain sealed through terminal freeze. Any accidental solution exposure is recorded and causes
permanent Development demotion; it never disappears through restarting a worker.
