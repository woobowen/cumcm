## 用户原文与 Agent 具体化必须分开

用户任务书第9节（行274）限定“每题最多4次新的模型CLI启动、独立数值checker最多4次、最终核验最多1次”，并明确“终局失败后不追加Final”。行292允许两题首轮完成、冻结当前结果后，对新通用 blocker 进行“最多一次明确的新候选修订与必要开发回归”。

第12节（行351）另设“全局最多两次功能候选修订，后续仅必要测试/文档收口，若必须再改shared则如实停止候选接受”。第11节明确本轮不必强行发版。第12节行357仍允许中立反例、旧终局只读重算、新开发可执行性、命令/恢复和依赖复现盘点。

**用户没有逐字定义“初始共享候选计为 revision 1”，也没有把第9节的统一修订写成不受全局上限限制的额外赠送次数。** 将初始 RC9 记为1，是主 Agent 在授权其制定冻结设计时采用的具体计数方案；不能倒写成用户直接指定的编号。

该方案确在结果前登记：协议在 `7ed9dd1` 已有 `functional_candidate_limit=2`；r1 于03:27:38 UTC冻结为 `functional_revision=1`，r2于03:44:25 UTC冻结为2，二者均绑定同一协议 SHA256 `3deae1f553830c7845d05d61f2041473bc9a85b1f0f50f558677484887e9dc61`。r1/r2记录分别在 `292d91b`/`1b34732` 提交，而首次 CLI 请求约03:47:23才开始。故这不是看到 R7-001 后才制造的计数。原设计的 `revision_policy` 还明确写“first shared subject…at most one unified second subject”。

在这个无明确用户冲突、已被用于实际执行的预登记口径下，初始计1具有本轮方法与证据契约约束。冻结文件不能限制用户后续新授权，但 Agent 不能为了当前失败自行改计数腾出第三个 subject。应把“预算为何已用完”的归因写清：这是前期采用并实际执行的计数方案及修订分配结果，不是声称用户要求必须在数值首轮前消耗两次。

## r1零数值启动不产生预算退款

r1→r2的六个映射变化包括两题设计root、三个测试文件及 `scripts/prepare_phase004c6_development.py`。core与科学模型代码相同，但 preparation **实际改变了运行行为**：由固定读取一份注册文件，改为读取当前registry指针、核验唯一case/path/hash/subject/root/design绑定。这不是单纯格式或报告改动。

supersession、shared freeze和两题r2 registration均在运行前将其记为revision2；supersession声明r1模型/checker/Final均为0。这个0支持“首次真实Development仍在r2上进行”，不支持“候选修订次数未消耗”。协议没有“未启动数值则退回候选次数”条款。将r2现在重命名为r1，或把下一修复继续标为revision2，都会事后改变已有执行口径。

因此，第9节的首轮后统一修订在实际执行层面尚未发生，但没有单独保留的全局次数可支撑它。两条上限应同时满足，不能把第9节解释成“全局两次之外必有一次”。反过来，也不能声称这次前置supersession是用户要求的最优预算分配；预算使用与停止后的正确性是不同问题。

## 每题4次CLI、2次模型进程的区别

独立逐字段检查两题design、r2 registration、terminal、execution evidence和ledger：限额均为4/4/1；terminal均FAILED，绑定revision2及同一subject。每题实际外层模型CLI调用四次：前两次 `execute` 返回3（非法Run ID），后两次返回0并产生数值模型进程。terminal分别记录 `actual_model_cli_requests=4` 与 `pre_execution_model_request_rejections=2`；ledger的 `model_cli_starts=2` 实际计数是两个数值子进程，名称容易混淆。

用户原文约束的是“模型CLI启动”，不是“成功拟合数”。非法Run ID虽未启动模型子进程，外层CLI确已启动，因此不能单靠ledger的2自动认定还剩两次外层启动。原始数据不应改成4个数值进程；应继续同时保留4次CLI/2次真实进程两个口径。

每题checker3次，账面还有1次；Final0次，账面还有1次。但两题已FAILED并冻结，第9节禁止终局后追加Final，故Final0不等于仍可在这些终局上使用1次。剩余checker次数也不能替代所需模型启动、重新授予Final或改变候选额度。新建root/更换case ID本身不会重置“每题”本轮累计限额。

## 可做与不能自行做的下一步

当前仍可在隔离synthetic scratch构造“plan缺scenario_hash→真实公共入口拒绝”的最小中立反例，保存失败命令与hash，并整理下一轮修复需要统一的默认值、回归入口及恢复步骤。它属于第12节明文允许的中立反例/可执行性收口；必须如实报告未修复、未接受，不能替代两题真实完成。本审查只读，未执行该反例或任何真实模型/checker/Final。

当前不能自行：增加第三个shared功能候选、事后将r1/r2重新编号退款、再启动每题第5次模型CLI、在FAILED终局追加Final、以新ID复制同题领取全新4/4/1，或把旧capture换subject后当成新候选实跑。仅增加中立PASS或再次审计同一负决定，不能解除真实通用阻断。
